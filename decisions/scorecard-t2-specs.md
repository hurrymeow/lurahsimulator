# Scorecard T2 specs

Three specs in `tests/e2e/scorecard-t2.spec.ts`, one per Unknown scorecard row. They read the running app through the existing `?debug` handle (`window.pakrt`, `window.pakrtDefs`); no `src/` change or new debug hook was added.

- **Row 27, coming back.** Reads the building and resident counts from `window.pakrt.s`, calls `save()`, reloads, passes the home screen with Continue, waits 5s, and reads the same counts. It runs `scanLegibility` on the screen at 5s and attaches a screenshot. It cannot prove the current goal and its progress are on screen, which is what the scorecard row asks for; it only proves the save comes back with the same counts and a legible screen, and it does not cover a real device's cold start.
- **Row 6, causes are legible.** Reads the newest line in `window.pakrt.log` after one tick, with a permit building added so the `queue` cause drains Popularitas (the first-drop warning's `SABAR_CAUSE` map in `src/sim/tick.ts`). It compares the title and body with `t('warn.sabarTitle')` and `t('warn.sabar.queue')` in the project's language, never a hard-coded sentence. It cannot prove every drop is named, only that the first queue-caused fall names its cause.
- **Row 3, growth shows on the map.** Loads the RT 3★ developer seed through Settings, then models 1★ and 2★ by dropping buildings whose kind a later star unlocks (`requires.stars`), and counts the same building list `src/render/map.ts` draws (`s.buildings` plus neighbours). It cannot prove a real player's map grows in the default view: the seed is one 3★ town trimmed back, not three saves reached by play, and the count is the draw list, not sprites measured inside the viewport.
