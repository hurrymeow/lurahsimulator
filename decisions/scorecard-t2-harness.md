# Scorecard harness reads the T2 specs (2026-11-07)

Rows 3, 6 and 27 now take their verdict from `tests/e2e/scorecard-t2.spec.ts` (#350) instead of reading Unknown.

- **How the results get in.** `npm run scorecard:t2` (`scripts/scorecard-t2.mjs`) runs the spec at 412px, once with `E2E_LANG=id` and once with `E2E_LANG=en`, and writes a Playwright JSON report per language to `scorecard/.cache/t2-<lang>.json`. `tests/scorecard/t2.ts` reads them; `report.test.ts` passes them to `buildScorecard`. `npm run scorecard` runs it between the bots and the report. `npm test` never runs e2e: the unit test parses a fixture report.
  - Counter: a results file the spec writes itself would be smaller (the JSON report embeds the row 27 screenshot, about 1 MB a language). The JSON reporter needs no spec change and keeps Playwright's own pass, fail and retry status, so it was kept.
- **Verdict rule.** Fail if any run failed or passed only on retry (TESTING.md item 2: flaky is a bug). Unknown if there is no report, a run was skipped, or row 27 lacks one of the two languages (its bar says "in both languages"). Pass only when every needed run passed first time. Rows 3 and 6 need one language; both run anyway.
  - Counter: Fail on flaky can make a nightly row flip on runner noise. That is the point: a flaky spec is not evidence.
- **Row 6** keeps its T1 part: Fail if any logged drop has no cause, else the T2 verdict. The spec checks one queue-caused fall in the Log sheet, not every drop; the evidence says so.
- **Row 3** is judged on the draw list of the trimmed developer seed, with N not set (any rise passes). The evidence says it is not sprites in view. GAME-DESIGN.md says N is set from a first measured run; that run is this one, and N stays open.
- **Row 27 reads Fail (user's call, option 1 under the Conformance protocol).** The spec now also checks that the same goal line is on screen 5s after the reload, and records (a test annotation, not an assertion) whether the goal's have and need rows show without a tap. The bar asks for "current goal and its progress on screen"; `decisions/goal-line-one-goal.md` keeps have and need off the closed pill, so the harness reads Fail with "progress is a tap away". GAME-DESIGN.md §8 and the pill decision stay as they are. Whether the pill or the bar should change is a TODO follow-up.
  - Counter: the progress is one tap away and the pill was a deliberate fix for a cut-off line, so Fail may overstate the problem. The row flips to Pass by itself if the pill ever shows progress closed, since the spec measures it.
- **Row 6 spec flaked (#350), fixed here.** Under load it failed about 1 run in 20: a random event waiting for an answer makes `tick()` return early, so no week passed and no warning fired. The spec now sets the pending event aside and repeats the setup for up to 6 weeks until the first fall is logged. 60 of 60 runs passed across all widths after the fix.
- **Nightly.** New job `scorecard-t2` in the Playwright container (about 3 min). The report job runs even when it fails, so rows 3, 6 and 27 then read Unknown instead of the whole scorecard being lost.
- **Approval.** Judged against GAME-DESIGN.md §8 items 3, 6, 27 and TESTING.md items 2 and 7 (`npm run scorecard` "runs the bots and specs"). Self-approved under the TODO approval rule.
